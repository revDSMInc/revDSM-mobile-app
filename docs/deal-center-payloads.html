revDSM Sales · Dynamic Deal Center

Deal Center Wire Reference

Every request the deal center fires, from opening a lead to Complete Job, with the web body and the mobile body side by side. Read in flow order — the stages are the rep's path through the screen, and each card names the moment the request leaves the device.

web · mhalt-revDSM-sales-frontend mobile · mhalt-revdsm-mobile the two differ

Scope. This is the dynamic (schema-driven) deal center — web sections/deal-center/ vs mobile screens/DynamicDealCenter/. The classic calculator (sections/lf-calculator/ · mobile screens/DealCenter/) shares the same endpoints but builds its own bodies and is not covered here. Every payload below was read out of the source, not reconstructed from a trace; the file and symbol are printed on each panel.

Mobile always resolves a calculator id (resolveLeadCalculatorId) and uses the calculator-scoped route.

This is the single biggest shape difference in the deal center. Drops

The negotiation ladder. One request per Decline / Secure, never on opening the sheet.

      "downPayment": 0, "balance": 10000 },
    { "dropedPrice": 8888,           // no _id → filed as new

Mobile useDynamicCalculators.ts → saveDropsNow
utils/drop-prices.ts → toDropPricePayload
{
  "dropPrice": [
    { "_id": "6a86b180…", "dropedPrice": 10000,
      "status": "declined", "paymentMethod": "check",
      "pricemarkup": "PAR + 8%",
      "downPayment": 0, "balance": 10000 },
    { "dropedPrice": 8888,
      "status": "accepted", "paymentMethod": "gs2521",
      "pricemarkup": "COST + 12%",
      "downPayment": 500, "balance": 8388,
      "paymentMethods": ["gs2521", "wf3672"] // omitted when empty
    }

Rules

dropPrice is a merge-by-_id subdocument array. A row that arrives with an _id updates that row; a row without one is filed as new; a row the payload omits is not deleted — it survives on the server, invisible to the rep. So nothing on either read or write path may drop a row, and mobile adopts the ids the server assigns (matched by price + status among unclaimed rows, never by index) so a re-save updates in place.

At most one row may be accepted. Web enforces it in four places inside handleSecurePrice; mobile centralises it in normalizeSingleAcceptedDrop and runs it on both sides of the wire, so a record already corrupted is repaired on open.

Mobile adds one rule web does not have: resulting a calculator whose every drop is declined secures the last round first. Without it the sold calculator carries no record of what the customer agreed to, and the portal board reads the accepted drop on a sibling calculator as the sold job. paymentMethods is kept for the same reason — re-opening a declined drop restores the financing plans it was negotiated with.

Agreements and order sheets. The clearest architectural split in the flow.

The moment a document is scanned or an agreement is generated — not at submit.

Mobile DynamicJobBuilderScreen.tsx → handleUploadDocs
{

  "status": "Sale",
  "selectedCalculatorId": "6a8299…",
  "jobBuilder": { /* the serialized state, status "draft" */ },

    { "name": "", "file": "JVBERi0xLjQ…", "type": "agreement" }

Web dynamic-job-builder.js

No upload here. Web keeps the files on jobState.agreements / .orderSheets as durable local references and converts them to base64 PDFs only at Complete Job (stage 08).

Delta

This is why mobile's submit mirror drops its documents. On mobile every document is already a LeadOutcomeDocument row by submit time — filed by this request, or by the /sign endpoint for a generated agreement. Re-sending the bytes at submit (as web does) filed a second row: identical base64Data and byte size, distinct _id and filePath, and an empty name — the duplicate agreement reported from the field.

The trade-off is the other direction: mobile pays a multi-MB upload per scan and web pays it once, at the end.

Divergence ledger

Every difference above, in one place, with the reason it exists.

StageDifferenceWhy it is not a bug
01 Mobile adopts a 409 on POST /appointments The date-filtered GET can miss an existing appointment (UTC/local off-by-one on lead_date); without this the flow drops into local, unsaved mode.
01 Mobile seeds entries on the first calculator; web sends {title, price} Convergent after one edit. Mobile's create is the same helper as the ＋ button.
02 Web's duplicate copies the source record; mobile copies the entries Mobile re-derives the rep-level defaults and lets the autosave write the rest.
02 No rename request on mobile Dynamic titles are derived from the entered values; the tab menu offers Duplicate and Delete only.
03 · 04 Mobile folds every rollout field into the debounced whole-calculator save; web writes each as its own PUT Fewer requests on a phone. Cost: each save re-asserts the rollout state, so freshness is bounded by the 1500 ms debounce.
04 Mobile omits paymentMethodLabel Derivable from the key against the plan catalog. Worth adding if a portal reader depends on the stored label.
03 · 04 priceScopeSig and inHome are mobile-only The first drives the "job scope changed — review the end price" warning across a reload; the second persists the Investment Center's monthly shortlist, which web keeps in local state.
05 paymentMethods[] on a drop row is mobile-only Re-opening a declined drop restores the financing plans it was negotiated with.
05 Mobile secures the last drop when a rep results an all-declined calculator Otherwise the sold calculator stores no record of the agreed price and the portal board attributes the sale to a sibling calculator that does have an accepted drop.
06 Mobile writes no outcome at result time The modal's answers are held in memory and land with the first draft autosave. A lead therefore has no outcome row until the job builder opens.
06 versatile / pineapple are mobile-only They do not exist anywhere in the web sales app. Carried so they rehydrate on reopen.
06 Mobile omits LFCalculator unless it is the real server document The backend subdocument requires createdBy / appointmentId / title; a partial one 500s the PUT.
07 Mobile files documents eagerly; web files them at submit Consequence: mobile must NOT re-send them in the submit mirror, or the backend files a second row (same bytes, empty name, new _id).
08 Mobile's leadData is assembled key by key; money is a normalised string The contract has a fixed key set. "" never 0: a zero reads as a real quoted figure on the portal.
08 Mobile sends paperWork: [] and downPaymentReceipt: [] The backend contract lists four document groups, and an absent key is not an empty one to a partial-update handler.
08 Mobile's mirror is calculator-scoped; web's is lead-scoped The bare lead-scoped PUT /lead/v1/{leadId}/outcome 404s on device and was removed app-wide from mobile.
08 Mobile sends leadResulted: "completed" at Build Job Web's dynamic flow only ever sends "active", so the portal's milestone never flipped to Complete.
09 Mobile's summary tiers come from stored totals Mobile's port of calculateResultUtil is not schema-aware, so the legacy column pricing returns nothing for a dynamic calculator.
